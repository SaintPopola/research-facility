# Windows build — status, path, and why it's deferred

**Status: not built yet (macOS-only in CI). Feasible, but a dedicated effort — not a
quick add.** This documents the exact path so it can be tackled deliberately, not by
burning blind CI cycles.

## Why it's harder than macOS
The macOS CI downloads a ready-to-run `HISE.app` and runs `HISE export`. On Windows:
- **No standalone `HISE.exe` is published** — the 4.1.0 release ships only
  `Hise.Installer.4.1.0.Windows.x64.exe` (a 20 MB *installer*, not a portable binary).
  Extracting a usable `HISE.exe` from it on a runner is unreliable.
- The HISE-recommended path is to **build HISE from source** on the runner
  (`tools/auto_build/build_ci.bat`) — a 30–60 min MSVC compile with its own IPP/toolchain
  setup, before you even export the plugin.
- **`export_ci` defaults to Visual Studio 2017** on Windows; `windows-latest` runners ship
  **VS2022**, so the toolset must be overridden or VS2017 build tools installed.
- **No public working GitHub-Actions YAML** exists for a full HISE Windows plugin build
  (forum thread 13215 confirms people do it, but "with annoying things along the way").

## The good news (the one real blocker is solved)
- **IPP is not required for Research Facility** — IPP/FFTW only matter for FFT work
  (convolution reverb), which RF doesn't use; Kiss FFT is the fallback. So IPP can be
  disabled, exactly like the macOS job already does (`USE_IPP="1"→"0"` in the `.jucer`,
  plus setting the VS exporter's *Use IPP (One API)* to `No`). In `export_ci`, IPP is off
  by default (you opt in with `-ipp`).

## The path (when someone invests the day)
1. **windows job on `windows-latest`.** Checkout + cache.
2. **Build HISE from source (CI variant):** clone HISE 4.1.0 + JUCE submodule, install the
   Steinberg VST3 SDK to `tools/SDK/VST3 SDK`, run `tools/auto_build/build_ci.bat` (produces
   a semi-optimized `HISE.exe`). Pin/override the platform toolset to the runner's VS2022 if
   VS2017 isn't present.
3. **Export the plugin:** `HISE.exe export_ci "XmlPresetBackups\ResearchFacility.xml"
   -t:instrument -p:VST3` (no `-ipp` → IPP off). This generates the VS solution + a
   `batchCompile.bat`.
4. **Patch the generated `.jucer`** the same way the macOS job does (USE_IPP=0,
   JUCE_VST3_CAN_REPLACE_VST2=0, strip any IPP header/lib paths).
5. **Build:** `Projucer.exe --resave AutogeneratedProject.jucer` then
   `msbuild AutogeneratedProject.sln /p:Configuration=Release /p:Platform=x64`.
6. **Artifact:** `ResearchFacility.vst3` (Windows has no AU). Add it to the installer story
   as a Windows `.exe`/Inno Setup installer (a separate, later task).

Pitfalls to expect: MSBuild/VS detection, Windows path-length limits (keep the workspace
path short), the AppConfig `ipp.h` include error if IPP flags leak through, and HISE's
global-AppData path assumptions.

## Recommendation
Defer until there's a concrete Windows buyer or a dedicated block of time. The macOS build
is a complete, sellable product on its own; Windows roughly doubles the market but is a
multi-hour, iteration-heavy job, not a drop-in. When ready, implement the job above as a
second `build_windows:` in `.github/workflows/build-plugin.yml`.
